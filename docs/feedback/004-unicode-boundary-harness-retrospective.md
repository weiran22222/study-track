## 2. 从黑盒失败到可验证通道

黑盒评估发现，Windows 原生命令行会在补充平面字符进入 JVM 前破坏它们：按 Unicode
码点计数本应有效的 200 个 emoji，在真实进程中被错误拒绝。Application 已经使用
`String.codePointCount`，因此问题不在标题业务校验，而在 Shell、Windows 原生参数和
Java 启动器之间的进程边界。

随后进行的 POC 没有把第一个可行猜想直接写入 Harness：

| 候选通道 | 实际结果 |
|---|---|
| PowerShell 7.6.3 的 `Windows`、`Standard`、`Legacy` 参数模式 | 200 个 emoji 进入 Java 前仍被破坏，方案被否证 |
| JDK 21 `@argfile` | 参数文件受本机 GBK 原生编码限制，UTF-8 文件仍不能传递 emoji，方案被否证 |
| 命令行传 ASCII 路径、JVM 内严格读取 UTF-8 标题文件 | 200 码点成功；201 码点返回 `2` 且数据哈希不变，POC 与正式实现均成功 |

最终实现保留内联标题，并增加互斥的 `--title-file` 输入。自动 Java 子进程测试和真实
JAR 验收都让 Unicode 内容只经过 UTF-8 文件进入 JVM，避免测试再次依赖已经确认不可靠的
原生命令行字符通道。

这一过程的学习是：跨进程编码问题需要在真实边界上做黑盒验证；单看 JVM 内的字符串单元
测试，无法证明字符在到达 JVM 之前没有丢失。POC 的价值也不只是证明最终方案可行，还在于
用相同边界否证看似更轻量的 PowerShell 7 和 `@argfile` 方案。

## 3. 实施完成不等于审查完成

无父对话子智能体完成标题文件端口、严格 UTF-8 实现、CLI 组合和自动测试后，主智能体独立
审查发现参数预处理器把负数 ID `-1` 误分类为选项。这是新增参数解析逻辑对既有内联
`rename` 行为造成的回归，不是标题文件读取本身的失败。

修复后，CLI 测试和真实组合入口测试都增加了负整数 ID 回归场景，证明 `-1` 继续进入任务
查询并返回 `Task -1 not found.`，同时不创建或修改数据文件；真实 JAR 复验还确认了负号
开头的内联标题仍可使用。对应命令、输出和 SHA-256 记录在
[证据 005](../evidence/005-unicode-safe-title-file-input.md#真实-jar-验收)。

本轮因此再次验证了两层反馈的不同作用：实施者测试覆盖已知规格，独立主审从变更引入的
解析机制出发寻找相邻回归；发现具体失败后，再把它固化为可重复执行的回归测试。

## 4. 状态漂移的两级处理

Unicode 功能进入主线后，`AGENTS.md` 中手工维护的阶段快照仍写着 `Harness v13` 和
`AC-01～AC-15`。第一次处理只把它同步为 `Harness v14`、`AC-01～AC-16` 并补充已实现
输入形式；这属于不改变既定语义的一级事实修正。

这次修正也暴露了更深层原因：没有明确版本协议的 Harness 编号、手工 AC 计数和完成清单
都会在下一次演进后再次过期，并且重复了 `SPEC.md` 与历史工件的职责。删除这些字段需要
判断默认导航应保留什么，因此没有被包装成另一次事实修正。学习者明确批准
[决策卡 013](../decisions/013-remove-volatile-harness-progress.md)后，才按二级流程移除重复
状态，改为由 `SPEC.md` 提供权威产品事实、由 `verify` 提供机械验收入口、由文档索引提供
历史理由。

提交历史保留了两步之间的区别：`87d585f` 先对齐当时事实，`a510f7a` 再实施经批准的
职责调整。先修正已知错误没有替代后续的人类判断，后续精简也没有把先前错误状态合理化。

## 5. 本轮学习结论

本轮事实让既有 Harness 分级与工件职责更具体：

1. 对权威、稳定且机器可观察的不变量，机械检查能把一次发现变成持续反馈。本轮对应实例
   包括真实 Java 子进程的 200/201 码点边界、负数 ID 回归测试，以及文档索引导航测试。
2. 对能够从权威来源推导出的副本，继续同步会制造新的漂移点。删除 `AGENTS.md` 中的
   Harness 版本、AC 计数和完成清单，比持续更新同一份派生状态更符合稳定导航的职责。
3. 机械检查只能判断已定义的不变量是否满足，不能决定项目应该追求什么目标、接受什么
   风险或承担多少维护成本。Unicode 输入方案的产品范围与导航职责调整都经过人类批准，
   POC、测试和 `verify` 为决定提供证据，但没有代替决定本身。

这三点是对本轮已发生工作的归纳，不是新增决策、验收标准或智能体权限。
