### 2.4 无父对话交接

`list`、`complete`、损坏数据三个切片使用了不继承父对话的新子智能体。它们没有
请求父对话中的产品或架构信息，并能从仓库恢复范围、非目标、分层和验收。

但这不能表述为“完全只靠仓库”：

- 委派消息仍提供了本机 JDK 21 安装路径；
- 委派消息仍提供了 Maven Central TLS 失败时可使用的本机 settings 路径；
- 这些属于执行环境信息，而非产品和架构知识。

因此当前证据支持：

> 产品、架构和工作约束已经能够无会话交接；干净机器上的执行环境自举尚未得到
> 完整验证。

## 4. 已知限制

以下事实不应被自动测试通过掩盖：

1. GitHub Actions `verify #1` 已在远程成功，环境自检和 33 个测试均有运行证据；
   但工作流启用了 Maven 缓存，这不是无缓存冷启动证明；
2. 远程运行报告 `actions/checkout@v4` 和 `actions/setup-java@v4` 的 Node.js 20
   运行时弃用警告；当前仍成功，但版本升级尚待人类决定；
3. 当前机器直连 Maven Central 存在 TLS 问题，完整冷启动依赖本机镜像或已有缓存；
4. 环境自检可以诊断 JDK、Wrapper、代理或证书问题，但按安全边界不会自动安装软件或
   修改机器配置；
5. Shade 仍会报告第三方 JAR 的模块描述重叠告警，当前判断为非阻塞；
6. JSON 的逐任务字段、重复 ID、`nextId` 一致性和数据迁移语义尚未进入规格；
7. 当前项目较小，尚未验证多智能体并行、worktree 隔离和合并冲突处理；
8. 执行计划较详细，它提高了交接确定性，也带来了编写和维护成本。

## 5. 候选改进，不代表已决定

| 候选项 | 预期收益 | 成本或风险 |
|---|---|---|
| 增加环境自举/冷启动检查 | 验证干净机器真正可运行 | 需要处理 JDK 与镜像差异 |
| 实际推送并运行 GitHub Actions | 验证远程合并门禁 | 涉及远程仓库和外部状态 |
| 定义更完整的数据结构不变量 | 提高损坏数据覆盖 | 可能引入迁移与兼容复杂度 |
| 压缩执行计划模板 | 降低每个切片的规划成本 | 可能减少交接上下文 |
| 尝试两个 worktree 并行任务 | 验证并行吞吐与合并策略 | 当前产品已经完成，需要新范围 |
| 增加周期性文档/架构检查 | 控制长期熵增 | 小项目阶段可能过度工程 |

## 6. 人类判断

以下内容必须由学习者参与填写，不能由智能体代替：

### 6.1 最有价值的机制

学习者结论：

1. Harness 的实现不是一蹴而就的，而是从最简单的闭环开始，再根据真实执行中暴露的问题逐步迭代完善。
2. 除了验证功能本身，还需要使用 ArchUnit、Checkstyle、CI 等机械门禁验证 Harness
   所定义的架构、代码规范和合并流程是否真正得到执行。

这意味着 Harness 不是项目开始前一次性设计完成的“完美规则集”，而是一个随项目共同演化的反馈系统。
最初只建立足以运行的规则与反馈闭环；发现新的失败模式后，再把经验固化为文档、测试或门禁。

### 6.2 成本最高但收益不确定的机制

学习者当前结论：暂时无法确定。

这是第一次完整运行该 Harness，目前没有与“更轻量 Harness”或“不使用 Harness”的对照数据，
因此不能仅凭主观感觉认定某项机制过重，也不应立即删除门禁。

下一轮重点观察执行计划的编写和维护成本。它提高了无父对话交接的确定性，但现有计划较为详细；
需要记录规划耗时、实现中被实际使用的内容以及计划失效次数，再决定是否压缩模板。

### 6.3 权限边界

学习者确认以下权限边界：

1. 智能体可以自主修复违反现有规格、架构或测试的实现问题。
2. 小型 Harness 修复必须先提供决策卡，说明问题、证据、拟议改动、收益、成本及验证方式；
   在人类知情且没有改变既定目标的前提下才可实施。
3. 改变项目目标、架构、验收语义、智能体权限、工具链或持续维护成本的重大 Harness
   变化，必须先获得人类明确批准。
4. 智能体不得仅因为技术上可行就扩大 Harness 范围。

该结论已固化到根目录 `AGENTS.md`，后续智能体无需依赖本次对话即可恢复权限边界。

### 6.4 下一轮优先级

学习者接受主智能体建议，选择“环境自举与冷启动检查”作为下一轮优先方向。

原因是无父对话子智能体虽然能从仓库恢复产品和架构约束，但仍需要委派消息额外提供本机
JDK/Maven 路径，说明执行环境知识尚未完成仓库化。下一轮先建立最小的环境声明、诊断和
CI 反馈闭环，不自动安装系统软件，也不把本地缓存构建描述为真正的冷启动证明。

该选择已经形成
[决策卡 001](../decisions/001-environment-bootstrap.md) 和
[执行计划 006](../exec-plans/completed/006-environment-bootstrap.md)。

## 7. 后续动作

只有第 6 节形成明确的人类结论后，才创建下一轮改进计划。不能因为某项技术上
“可以做”，就默认它值得做。

学习者选定的环境自举改进已经完成：

- `AGENTS.md` 现在提供环境说明和两个平台自检入口；
- 默认 Java 17 的失败路径与 JDK 21 的成功路径均已实际验证；
- CI 在完整 `verify` 前运行 POSIX 自检；
- 3 个结构回归测试保护入口、文档、共享反馈契约和 CI 调用顺序；
- JDK 21 下完整 `verify` 的 33 个测试通过。

远程 `verify #1` 随后成功运行，证明 GitHub 上的环境自检和完整门禁可以执行。由于工作流
启用了 Maven 缓存，这仍不代表无缓存冷启动已经验证。远程运行还暴露了 Actions Node.js
运行时弃用警告，是否升级相关 Actions 版本需要新的 Harness 决策。
