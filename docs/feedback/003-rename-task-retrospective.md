# 第三次 Harness 实战复盘：rename 三级流程

状态：已完成

日期：2026-07-28

## 1. 复盘问题

`rename <id> <new-title>` 改变现有产品规格，完整经历了人类批准、规划 PR、无父对话
子智能体实施、功能 PR、最终主线验证和收尾 PR。本轮复盘评估哪些机制真正减少了错误，
以及哪些流程成本没有带来同等保障。

## 2. 客观事实

| 观察项 | 结果 |
|---|---|
| 规格批准前的冷启动 | 子智能体发现编辑任务被排除，停止编码并请求人类决定产品语义 |
| 规格批准后的冷启动 | 无父对话子智能体从仓库恢复范围、分层、失败边界和验证方法并完成实现 |
| 范围控制 | 没有扩大为通用编辑、迁移、依赖、CI 或远程权限变更 |
| 自动验证 | 新增 21 项测试，完整门禁共 78 项测试通过 |
| 远程流程 | 规划 PR #15、功能 PR #16、收尾 PR #17 均通过受保护流程 |
| 最终结果 | AC-15 在受保护 `main` 上实现并通过最终远程 `verify` |

完整产品行为以 `SPEC.md` 2.7 节与 AC-15 为准；实际命令、哈希和证据边界保存在
`docs/evidence/004-rename-task.md`。本复盘不重复这些内容。

## 3. 最大价值

最大价值是 `SPEC.md` 与验收标准形成的仓库内产品合同：

1. 规格批准前，它让冷启动智能体知道编辑功能尚未获授权，从而避免越权编码；
2. 规格批准后，它让另一个无父对话智能体无需重新猜测输出、退出码、幂等与失败语义；
3. 自动测试可以直接映射 AC-15，避免代码完成后再因产品语义不一致而返工。

这说明高价值来自明确且权威的产品合同，而不是文档数量本身。

## 4. 最大成本

最大成本是重复工件加独立收尾流程：

- 决策卡、`SPEC.md` 和执行计划多次表达同一产品协议，存在维护和漂移成本；
- 证据与计划又重复记录部分实现和验证结果；
- 三个 PR 分别触发审查与 CI，收尾 PR 主要把 GitHub 已有结果重新写回仓库。

收尾 PR 在本次实战中提供了完整教学样本，但它的增量保障小于规格先行、功能测试和受保护
功能 PR。该结论不表示远程结果可以不验证，只表示远程验证默认由 GitHub 保存即可。

## 5. 改进决定

学习者批准决策卡 011：

- 决策卡只解释为什么选择，`SPEC.md` 独占完整产品协议；
- 执行计划只保存实施步骤、风险和验证方法，证据只保存实际事实与边界；
- 第三级默认使用规划 PR 与功能 PR；
- 功能 PR 可基于真实本地事实更新并归档计划和证据，但不得预先声称合并后结果；
- 最终 `main` 的远程 `verify` 仍必须检查，结果默认以 GitHub PR/Actions 为权威记录；
- 只有存在必须回写的合并后外部状态、部署/迁移/远程权限变化、实际结果偏差或遗留事项
  时，才创建独立收尾 PR。

## 6. 保留的保障

本轮优化不减少人类产品决策、规格先行、自动测试、架构与代码门禁、受保护 PR、必需
`verify` 和最终 `main` 验证。优化目标是减少同一知识的重复表达，而不是降低验收标准。
