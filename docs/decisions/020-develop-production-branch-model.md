# 决策卡 020：develop 集成与 main 生产发布分支模型

状态：已批准，待实施

日期：2026-07-28

## 问题

当前所有日常集成与稳定基线都汇入 `main`。随着 Harness 实验增加，同一长期分支同时承担
日常集成和发布边界，无法清晰表达“已经通过日常验证”与“已经获得人工发布批准”的区别。
引入第二条长期分支会改变默认 PR 目标、分支保护、CI 分支流判断和紧急修复回流路径，
属于第三级 Harness 变更，必须先规划安全迁移。

StudyTrack 当前没有真实部署流程。即使 `main` 被定义为生产发布基线，也不得把其中提交
描述为已经部署到任何环境。

## 候选方案与取舍

### A. 继续只使用 main

- 收益：分支和保护配置最简单；
- 成本：日常集成与人工发布批准继续共享同一边界。

### B. develop 日常集成，main 生产发布基线

- 收益：普通变更先在 `develop` 汇总验证，只有经人工批准的 release PR 才进入 `main`；
- 成本：需要安全迁移默认分支、复制并验证保护、增加分支流检查和 hotfix 回流规则。

选择本方案。

## 人类决定

学习者于 2026-07-28 明确批准以下目标模型：

- `develop` 取代 `main`，成为日常集成分支和 GitHub 默认分支；
- 普通 `codex/*` 分支从最新 `develop` 建立，并通过 PR 合入 `develop`；
- `main` 作为经人工发布批准的生产发布基线，正常只接受 `develop → main` release PR；
- 人工发布批准必须记录在 release PR 中，不能由 CI 成功或默认分支身份替代；
- 当前没有真实部署；`main` 只表示发布基线，不表示已经部署；
- `hotfix/*` 从最新 `main` 建立，通过 PR 修复 `main`，随后必须通过 PR 同步回
  `develop`；
- `develop` 与 `main` 都必须要求 PR、必需 `verify`、与目标分支保持最新、管理员不可
  绕过，并禁止强制推送和删除。

## 分支流协议

- 普通变更：`develop → codex/* → develop`；
- 正常发布：`develop → main`；
- 紧急修复：`main → hotfix/* → main`，随后 `main → develop` 回流；
- 除明确的 hotfix 回流外，普通 PR 的 base 必须是 `develop`；
- 指向 `main` 的 PR 只允许 head 为 `develop` 或 `hotfix/*`；
- 不允许直接推送两条长期分支，也不允许以管理员身份绕过门禁。

分支流检查的精确事件契约、迁移顺序和首次自举验证以
[执行计划 017](../exec-plans/017-develop-production-branch-model.md)为准。

## 保护与远程事实

迁移必须先创建 `develop`，再完整配置并回读其保护，最后才把 GitHub 默认分支改为
`develop`。任何时刻都不得让未保护分支成为默认分支。`main` 的既有保护在整个迁移中
保持启用；两条长期分支的保护最终都要求：

- PR 合并边界；
- 必需状态检查 `verify` 且要求与最新目标分支同步；
- 管理员不可绕过；
- 禁止强制推送和删除。

GitHub 的分支 ref、默认分支、Branch Protection、PR、检查和 Actions 结果是远程事实的
权威来源。历史文档只解释意图，实施时必须逐步通过 GitHub 回读，不得凭本地状态或本文
声称远程迁移已经发生。

## 风险等级

这是第三级变更：它改变默认分支、两条长期分支的远程保护和允许的 PR 拓扑，并包含多个
有顺序依赖的外部状态变化。采用“规划 PR → 实施 PR → 首次 release PR → 最终 main
验证”的完整流程；禁止永久迁移绕过。

## 非目标

- 不在规划阶段创建远程 `develop`、修改默认分支或保护规则；
- 不增加真实部署、环境、制品发布、版本号或自动发布；
- 不改变产品行为、Java 架构、数据格式、依赖或远程权限；
- 不要求审批人数、签名提交、线性历史、合并队列或新的外部服务；
- 不把 `main`、release PR 或成功 CI 描述为部署证据。
