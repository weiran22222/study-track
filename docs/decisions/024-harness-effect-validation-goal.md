# 决策卡 024：以 Harness 落地效果验证为项目终极目标

状态：已批准（规划阶段，尚未改变活跃 Harness 行为）

日期：2026-07-29

## 问题

当前 `SPEC.md` 把 StudyTrack 描述为本地 Java CLI，并说明本版本用于验证一套最小
Harness。这正确限定了产品行为，却容易被误读为“持续交付 CLI 功能就是项目的终点”。
如果以功能数量、PR 数、文档数量或流程步骤数量代替结果判断，Harness 即使已经合入仓库，
也无法说明它是否提高了智能体交付的正确性、自主性、反馈质量或可维护性。

学习者需要纠正目标层级，并为后续 Harness 变化建立一个最小、可审计、不会制造重复工件
的效果判断框架。

## 人类纠正

学习者于 2026-07-29 明确纠正：

- 项目的终极目的不是把 StudyTrack CLI 本身持续做大；
- 终极目的是学习、验证并演进 Harness Engineering 实践，判断 Harness 落地后实际产生
  了什么效果；
- `https://github.com/deusyu/harness-engineering` 是主要学习来源；
- StudyTrack CLI 只作为边界稳定、结果可机械验收的受控实验载体。

这项纠正改变项目 Harness 的长期目的和评估语义，不改变当前产品协议，也不授权增加
`SPEC.md`“本版本不包含”的功能。

## 三层目标边界

### 1. 终极目标

StudyTrack 仓库用于通过可追踪的真实变更循环，学习、验证和演进一套让“人类掌舵、
智能体执行”更可靠的 Harness Engineering 实践。Harness 只有在预先说明的观察单元中
改善交付结果，且收益没有被人类负担或维护成本抵消时，才可称为产生了正向效果。

## 什么算 Harness 效果

“落地”只表示 Harness 变化已经按门禁进入目标分支；“效果”表示在明确的观察单元中出现
了可追踪结果。每次评估先写明变化、预期作用、观察单元和可用基线，再按与假设相关的维度
记录实际证据、反例和成本：

1. **结果正确性**：产出是否符合批准的产品、架构、权限和验收边界；是否减少漏测、
   越界实现、假成功或回归，而不只看最终一次测试为绿；
2. **自主性与人类掌舵负担**：在目标和边界明确后，智能体能否减少重复澄清、人工补救、
   微观指挥和审查往返；必要的人类产品决定不能被误记为 Harness 失败，也不能用智能体
   自行扩大权限来换取“自主”；
3. **反馈回路有效性**：测试、lint、guard、evaluator 或运行诊断能否及时发现真实问题，
   给出位置、不变量、原因和修复方向，并支持下一轮收敛；单纯增加检查数量不是效果；
4. **可复现性与可追踪性**：另一 evaluator 能否从仓库、精确 Subject SHA、命令和
   GitHub 记录重建验证对象与结论边界；记录多不等于可追踪，关键是事实能绑定到同一对象；
5. **交付效率**：达到同等正确性与风险边界所需的历时、失败修复轮次、等待和人工操作是否
   改善；不能用 PR 数、提交数、代码量、智能体数量或流程步骤数量单独代表效率；
6. **熵与维护成本**：是否引入重复协议、易漂移链接、脆弱检查、持续运行成本、认知负担或
   后续清理工作；短期加速若转化为长期高成本，不算无条件正向效果。

不强制把六个维度压成一个总分，也不要求每次变化同时改善所有维度。结论必须对应预先声明
的假设，说明改善、无明显变化、退化或证据不足，并显式保留权衡。没有可靠基线时只能记录
现状或建立后续基线，不能补造历史耗时、干预次数、缺陷率或归因关系。一次 PR 合并、
一次 `verify` 通过、一个 evaluator `PASS` 或新增大量流程，只是交付/证据事实，不单独
证明 Harness 有效。

## 最小可审计框架

采用“最小评估声明 + 复用现有记录”的方式：

- 评估开始时记录 Harness 变化与因果假设、观察单元、适用维度、基线或明确的无基线状态；
- 完成后记录实际结果、证据定位、反例/残余缺口、维护成本和
  `正向 | 混合 | 无明显效果 | 负向 | 证据不足` 结论；
- 优先复用 PR diff/review、Actions、冻结 SHA、generator 自检、evaluator 报告和现有
  反馈记录；这些记录能覆盖字段时，不强制再创建独立 evidence 文件；
- 只有跨多个 PR 的长期观察、实际结果偏离计划、需要保留的新知识或外部状态无法由现有
  权威记录表达时，才增加专门反馈/证据工件；
- 评价应比较“达到同等结果边界的成本与质量”，避免奖励做更多流程、文档或代码。

具体字段、证据边界和结论规则将在功能 PR 的稳定仓库级 Harness 目的/评估文档中形成。

## 候选方案与取舍

### A. 继续把 CLI 功能交付当作终点

- 收益：目标直观，现有产品验收可以直接计数；
- 成本：把实验载体误作研究目的，会奖励范围扩张，也无法判断 Harness 是否带来收益。

### B. 直接复制上游仓库的方法、结构和指标

- 收益：能快速得到完整术语和大量实践；
- 成本：上游是持续演进的学习项目，场景、规模和假设不同；复制会制造第二套权威、
  重复内容和未经本地验证的流程成本。

### C. 建立本地稳定目的与最小效果框架，以 CLI 为受控载体

- 收益：明确目标层级，用本仓库证据验证所学实践，并保留 `SPEC.md` 的产品权威和既有
  门禁；通过复用 PR/Actions/evaluator 记录控制工件熵；
- 成本：需要维护一份稳定目的文档和少量机械导航检查；效果归因仍需谨慎，不能由单次任务
  自动证明。

选择方案 C。

## 决定与最小实施方向

使用“规划 PR → 功能 PR”的第三级流程：

- 功能 PR 新增一份专用、稳定的仓库级 Harness 目的/评估文档，保存三层目标、效果维度、
  最小评估字段、证据复用和解释边界；
- `AGENTS.md` 与 `docs/README.md` 只增加简短导航和权威边界，不复制评估手册；
- `SPEC.md` 继续独占产品行为与验收标准，StudyTrack 继续是实验载体；本变化不增加、
  删除或改写 CLI 行为；
- 扩展现有文档导航测试，机械确认稳定文档存在、入口可发现、产品/Harness 权威不混淆、
  六个效果维度与上游“学习输入而非本地权威”边界没有被无意删除；
- 不新增运行服务、度量平台或强制独立证据文件。能由现有 PR、Actions 和 evaluator
  记录证明的事实继续以这些记录为准。

详细文件范围、同 SHA 验证和 GitHub-only 集成顺序见
[执行计划 021](../exec-plans/021-harness-effect-validation-goal.md)。

## 风险等级、当前边界与回退

这是第三级 Harness 变化：它纠正项目终极目的并新增长期评估语义，影响未来 Harness
选择，必须先由规划 PR 固化决定和计划，再由功能 PR 激活稳定导航与机械检查。

本规划 PR 只允许新增本决策、活跃计划 021 和索引项。它不修改活跃 Harness 行为、
`AGENTS.md`、`SPEC.md`、`ARCHITECTURE.md`、脚本、测试、CI、产品代码、依赖、权限、
分支保护或部署，也不声称已经观察到任何 Harness 效果。

规划或功能 PR 合并前可关闭对应 PR。功能合入后如框架造成误导、重复记录或维护负担，
通过新的受保护 Harness PR 修正或回退稳定文档、导航和测试；不得删除真实的 PR/Actions/
evaluator 记录、绕过 required `verify`，也不得把回退描述为抹除已经观察到的负面结果。
