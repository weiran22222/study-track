# 决策卡 010：重命名单个任务

状态：已验证

日期：2026-07-28

## 问题

StudyTrack 可以添加、查看、完成和删除任务，但用户无法修正已有任务的标题。当前
`SPEC.md` 明确把编辑任务排除在版本范围外，因此智能体不能仅因实现简单就自行增加编辑
能力。

重命名会改变用户可观察的产品行为和验收语义，并需要决定标题校验顺序、幂等行为、
不存在任务、损坏数据和写入失败等边界，属于第三级变更。

## 候选方案

### A. 不增加编辑能力

保持当前最小产品范围。

- 收益：不增加写入路径和维护成本；
- 成本：用户只能删除错误任务后重新创建，无法保留原 ID 和完成状态。

### B. 删除后重新添加

把重命名解释为删除旧任务并创建新任务。

- 收益：可以复用现有命令；
- 成本：会改变 ID、完成状态和任务顺序，也会消耗新的 `nextId`，不符合“只改标题”的
  用户意图。

### C. 提供通用编辑命令

一次支持标题、完成状态或其他字段的修改。

- 收益：未来扩展能力更强；
- 成本：产品协议和参数组合明显扩大，超出本次最小需求。

### D. 只重命名单个任务

增加显式的 `rename <id> <new-title>` 命令，只修改指定任务标题。

- 收益：保留 ID、完成状态、`nextId` 和其他任务，范围清晰；
- 成本：增加一条受失败安全约束的持久化写入路径。

选择本方案。

## 人类决定

学习者于 2026-07-28 明确批准：

1. 把单任务标题重命名加入当前产品范围；
2. 未完成和已完成任务都可以重命名；
3. 新标题复用 `add` 的规范化、长度限制和错误信息；
4. 归一化后的新标题与原标题相同时按成功处理，但不得写入数据；
5. 重命名失败必须保留原始数据；
6. 第一版只修改标题，不引入通用编辑、批量、交互或撤销能力。

## 产品协议

- 命令：`rename <id> <new-title>`；
- 处理顺序：Picocli 先解析 ID，Application 再校验标题，标题有效后才读取任务；
- 标题规范化：先使用 Java `String.strip()` 去除首尾空白，再要求包含 `1..200` 个
  Unicode 码点；
- 标题无效：stderr 输出
  `Task title must contain between 1 and 200 characters.`，退出码 `2`，不得读取、
  创建或修改数据文件；
- 成功修改：stdout 输出 `Renamed task <id>.`，退出码 `0`；
- 成功修改只改变指定任务的 `title`，其 `id` 和 `completed` 保持不变，`nextId`、其他
  任务内容和相对顺序保持不变；
- 幂等路径：归一化后的新标题与持久化原标题相同时，stdout 输出
  `Task <id> already has that title.`，退出码 `0`，不得写入数据文件；
- 不存在：stderr 输出 `Task <id> not found.`，退出码 `2`，不得修改数据；
- 非整数 ID：由 Picocli 返回参数错误和退出码 `2`，不得访问数据；
- 数据文件不存在：按任务不存在处理，不创建文件；
- JSON 损坏或持久化失败：退出码 `1`，不得覆盖或部分修改原文件；
- 参数次序还意味着“标题无效且任务不存在”时先报告标题错误，不读取数据。

权威行为已写入 `SPEC.md` 2.7 节和 AC-15；AC-15 已实现，并通过本地自动测试、真实
JAR 验收、受保护功能 PR 和最终 `main` 远程验证。

## 不变边界

- 不修改任务 ID；
- 不通过 `rename` 修改完成状态；
- 不实现通用字段编辑、批量重命名或交互式编辑器；
- 不保存标题历史，也不实现撤销；
- 不修改 JSON 字段或执行数据迁移；
- 不改变现有命令的输出和退出码；
- 不修改 CI、分支保护、依赖或 Harness 权限。

## 架构约束

标题校验与重命名用例属于 Application。CLI 只能解析参数、调用 Application 并映射输出
与退出码，不得直接访问文件系统或 Jackson。Infrastructure 通过现有 Repository 端口和
原子写入策略持久化修改后的任务集合。

## 第三级流程

1. 本决策卡、`SPEC.md` 2.7 节、AC-15 和执行计划 013 先通过受保护的规划 PR；
2. 规划合并后，由后续子智能体在独立功能分支实施，不把本规划描述为功能完成；
3. 主智能体审查实现并独立复跑定向测试、真实 JAR 场景和 JDK 21 完整 `verify`；
4. 功能通过受保护 PR 合并，并在最终 `main` 回查远程 `verify`；
5. 保存实施证据，必要时使用独立归档变更完成三级流程收尾。

## 验收

- `SPEC.md` 明确重命名协议和 AC-15；
- Application、Repository 和 CLI 分层保持正确；
- 标题校验顺序、成功、幂等、不存在、无文件、非整数、损坏 JSON 和写入失败路径有
  自动验证；
- `id`、`completed`、`nextId`、其他任务和原始文件失败安全得到验证；
- 使用构建后的真实 JAR 验证最小成功、幂等和失败无副作用场景；
- JDK 21 下完整 `verify` 通过；
- 功能通过受保护 PR 合并并在最终 `main` 重新验证。
