# 决策卡 011：精简第三级工件与收尾流程

状态：已接受

日期：2026-07-28

## 问题

`rename` 第三级实战成功消除了产品语义猜测，但同一协议同时出现在决策卡、`SPEC.md`、
执行计划和证据中，并使用规划、功能、收尾三个 PR。重复表达和独立收尾增加了维护与
CI 成本，却没有为每次变更都提供等量的新保障。

## 候选方案与取舍

### A. 保持三个 PR 和重复的自包含工件

- 收益：每份工件可以单独阅读，合并后事实也能写回仓库；
- 成本：同一知识容易漂移，规划与收尾的重复维护成本高。

### B. 取消规划和证据工件

- 收益：流程最短；
- 成本：会削弱规格先行、无上下文交接和证据边界，不接受。

### C. 保留必要工件，明确单一职责并默认使用两个 PR

- 收益：保留人类决策、规格先行和验证，同时减少重复知识与机械收尾；
- 成本：合并后的远程结果通常只保存在 GitHub，需要在确有必要时追加收尾 PR。

选择本方案。

## 人类决定

学习者于 2026-07-28 明确批准：决策卡、规格、执行计划和证据各自承担单一职责；第三级
默认从三个 PR 精简为规划 PR 与功能 PR；只有合并后外部事实、部署/迁移/远程权限变化、
实际结果偏差或遗留风险需要仓库记录时，才创建独立收尾 PR。

## 决定

- 决策卡保存原因、候选方案、取舍和人类选择，不复制完整产品协议；
- `SPEC.md` 是当前完整产品行为和验收标准的唯一权威；
- 执行计划引用 `SPEC.md`，保存实施步骤、风险和验证方法，不复制完整产品协议；
- 证据只保存实际命令、结果、哈希和证据边界；
- 第三级默认使用“规划 PR → 功能 PR”。功能 PR 可以根据已发生的本地实施事实更新证据
  并归档计划，但不能预先填写合并、最终 `main` 提交或远程 CI 结果；
- 功能合并后仍须验证最终 `main` 的 `verify`。GitHub PR 与 Actions 是远程 CI 的权威
  记录，默认不重复抄回仓库；
- 只有人类决定中列出的情形才使用独立收尾 PR。

本决定细化并部分取代决策卡 006 中“第三级必要时使用独立归档变更”的默认做法。
决策卡 006 的风险分级、升级条件及所有门禁边界继续有效。

## 不变边界

- 不削弱人类产品决策、规格先行、自动测试、受保护 PR、必需 `verify` 或最终 `main`
  验证；
- 不允许用“GitHub 是权威记录”为理由省略远程验证；
- 不改变产品行为、架构、代码、测试、CI、分支保护或远程权限；
- 不改写已有历史工件，也不把新规则追溯应用为历史事实。

## 实施与验收

这是局部、可逆、不改变产品与门禁的二级 Harness 调整。使用一个受保护 PR 更新本决策、
`AGENTS.md`、文档索引和 `rename` 复盘；不创建执行计划、证据或独立收尾 PR。

- `AGENTS.md` 明确工件职责、默认两段式流程和独立收尾触发条件；
- `rename` 复盘记录形成该决定的实际证据；
- Harness 版本更新为 v13，AC-01～AC-15 的实现状态保持不变；
- 文档导航测试与 JDK 21 完整 `verify` 通过。
