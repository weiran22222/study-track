# 决策卡 032：首次 Harness 文档与协议熵审计

状态：已批准，与本卡同一受保护 PR 实施

日期：2026-07-30

## 问题

现行分支协议已经把 `develop` 定义为普通集成的长期分支，把 `main` 定义为经人工批准的
release/hotfix 长期分支，但 `WORKFLOW.md` 第三级流程和所有级别不变边界仍残留
main-only 措辞。`DocumentationNavigationTest` 又机械保护该旧措辞，形成当前协议与测试
互相强化的语义漂移。

同时，历史索引没有明确历史工件中的状态、待办和“尚未发生”陈述只受各自证据截止点
约束，读者可能把历史记录误读为实时状态。

## 用户批准

用户于 2026-07-30 明确批准首次 Harness 文档与协议熵审计的最小清理。实施范围依据批准
目标收敛为当前协议、导航测试、历史索引和能力边界描述，不批量回填或改写历史工件。

本调整可逆、范围局部，不改变产品、架构、权限、工具链或远程状态，按第二级小型 Harness
决策实施。

## 候选方案与取舍

### A. 保留现状

- 收益：没有文档 diff；
- 成本：旧 main-only 语义继续与当前 develop/main 分支模型冲突，并被测试固化。

不选择。

### B. 批量回填历史工件

- 收益：历史文字表面上与当前状态一致；
- 成本：破坏工件的原始证据边界，可能把后来发生的事实倒写进过去记录。

不选择。

### C. 只清理当前协议与导航边界

- 收益：恢复当前权威协议、机械断言和历史读取方式的一致性，同时保留历史原貌；
- 成本：历史读者必须结合工件截止点、当前根级权威文档和 GitHub 远程记录判断现状。

选择本方案。

## 决定

- `WORKFLOW.md` 明确普通集成最终进入 `develop`；release 与 hotfix 修复的生产目标为
  `main`，hotfix 随后必须回流 `develop`；
- 合并后远程结果只以 PR 的实际目标长期分支为准，`develop` 与 `main` 的保护和
  `verify` 都不得绕过；
- `DocumentationNavigationTest` 保护上述当前不变量，不再机械要求旧 main-only 措辞；
- `docs/README.md` 明确历史状态、待办和“尚未发生”陈述绑定各自证据截止点；当前事实
  依根级权威文档，远程事实依 GitHub；
- 能力图只记录这次人工审计的能力与边界，不建立定时扫描、评分或自动维护机制。

## 边界

- 不修改 `SPEC.md`、`ARCHITECTURE.md`、`AGENTS.md`、产品代码、CI、脚本、构建配置或
  远程配置；
- 不批量回填或改写既有决策、计划、证据和反馈正文；
- 不新增定时扫描、评分、服务、自动维护 PR 或持续运行成本；
- 不把本次清理、测试、`verify`、evaluator 或 PR 结果写成 Harness 正向因果效果；
- 不预写 evaluator `PASS`、required CI、合并、目标长期分支更新或其他远程成功。

## 验收

- 当前工作流与导航测试共同保护 develop/main 分支模型和实际目标长期分支验证；
- 历史索引明确证据截止点、当前事实与远程事实的权威边界；
- 定向 `DocumentationNavigationTest` 与 JDK 21 下完整 `.\mvnw.cmd verify` 实际通过。
