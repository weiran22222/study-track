# 决策卡 005：架构导航地图降粒度

状态：已验证

日期：2026-07-27

## 问题

并行实现 `show` 与 `summary` 后，`ARCHITECTURE.md` 的文件级目录地图没有同步列出新增类，
并且仍列出一个不存在的测试文件。收尾阶段已经手工修正事实，但同类漂移仍可能再次发生。

最初建议增加机械检查，强制所有 Java 文件都出现在地图中。学习者指出了更基础的问题：
架构文档是否本来就不应包含全部代码文件。

## 人类判断

学习者认为需要先质疑完整文件地图这一前提，而不是直接增加新的机械门禁，并同意继续按
修正后的方向推进。

## 备选方案

### A. 完整文件地图加机械一致性检查

每个生产 Java 文件必须出现在 `ARCHITECTURE.md`，文档中的每个文件也必须真实存在。

- 收益：可以机械阻止地图漂移；
- 成本：普通类增删都会修改架构文档和检查结果；
- 风险：把高频文件清单误当成稳定架构，让智能体为了过门禁而机械维护重复信息。

不选择。

### B. 包级导航加少量关键入口

目录图只展示稳定的包、职责和少数关键入口，并明确它不是完整文件清单。完整文件集合由
Git、IDE 或 `rg --files` 查询，依赖方向继续由 ArchUnit 保护。

- 收益：保留新智能体的快速导航，同时减少文档漂移和维护成本；
- 成本：文档不能直接列出每个实现类；
- 风险：关键入口选择需要保持克制，不能重新膨胀为完整清单。

选择本方案。

### C. 完全删除目录地图

只保留文字形式的分层规则。

- 收益：维护成本最低；
- 成本：新智能体失去快速定位模块和入口的地图。

不选择。

## 决定

1. 将 `ARCHITECTURE.md` 第 3 节改为“包级导航与关键入口”；
2. 包级地图只展示 `bootstrap`、`cli`、`application`、`domain`、`infrastructure`；
3. 只列出启动、根命令、应用服务、持久化端口和当前持久化实现等关键入口；
4. 明确该节不是完整文件清单，查询文件应使用 Git、IDE 或 `rg --files`；
5. 不新增全文件地图测试、脚本或 CI 门禁；
6. 不改变第 4、5 节的分层、依赖方向和 ArchUnit 规则。

## 为什么这是 Harness 修复

Harness 不仅可能缺少约束，也可能包含维护成本高于收益的错误抽象。本次修复降低导航工件
的变化频率，让文档聚焦稳定决策，同时把可机械验证的依赖规则继续交给 ArchUnit。

## 验收

- 第 3 节不再表现为完整源码文件树；
- 五个包、职责和五个关键入口可以快速定位；
- 文档明确说明如何查询完整文件集合；
- 技术栈、分层、依赖、持久化和验证规则保持不变；
- 不新增测试、脚本、依赖或 CI 配置；
- JDK 21 下完整 `verify` 仍然通过。
