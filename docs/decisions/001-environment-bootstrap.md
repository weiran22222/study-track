# 决策卡 001：环境自举与冷启动检查

状态：已实现

日期：2026-07-27

## 问题

无父对话子智能体已经能够从仓库恢复产品、架构和工作约束，但此前的委派消息仍需额外提供
本机 JDK 21 路径和 Maven TLS 失败时使用的本地 settings 路径。这说明仓库尚未完整承担执行环境
的导航和诊断责任。

## 证据

- `pom.xml` 使用 Maven Enforcer 要求 JDK 21，但机器默认 `java --version` 当前返回 Java 17；
- Maven Wrapper 已固定 Maven 3.9.12，但新参与者仍需知道如何判断 Wrapper 是否可用；
- GitHub Actions 声明使用 JDK 21，但尚未在远程仓库实际运行；
- 本机访问 Maven Central 曾出现 TLS 问题，之前依赖对话中提供的机器专属 settings 路径绕过。

## 人类决策

2026-07-27，学习者批准优先建设“环境自举与冷启动检查”。

## 拟议改动

建立最小环境反馈闭环：

1. 在仓库内明确声明 JDK 21 和 Maven Wrapper 是唯一受支持的构建入口；
2. 提供 Windows 与 macOS/Linux 的环境自检入口；
3. 自检失败时报告检测值、要求值、修复方向、后续验证命令和权威文档；
4. 让 CI 在执行完整 `verify` 前运行同一套 Linux 自检；
5. 为关键环境契约增加低成本回归保护。

## 收益

- 新智能体不需要从父对话获取机器路径就能发现环境不合格；
- Java 版本、Wrapper 缺失和基础启动失败能够在完整构建前快速暴露；
- 本地与 CI 对环境要求使用相同语言；
- 为以后真正的干净机器冷启动实验建立可重复入口。

## 成本

- 需要同时维护 PowerShell 与 POSIX shell 两个薄入口；
- 环境差异无法仅靠静态配置测试完全覆盖；
- 网络、证书和代理问题仍可能需要机器或组织级处理；
- CI 接入只有在远程实际运行后才能成为经验证据。

## 权限与安全边界

- 脚本不得自动安装 JDK、修改系统 PATH 或修改用户级/全局 Maven 配置；
- 不得把机器专属绝对路径、私有镜像或凭据写入仓库；
- 不得把已有依赖缓存上的成功描述为真正的冷启动证明；
- 若需要新增安装器、容器、版本管理器或组织级镜像，必须创建新的决策卡并再次取得人类批准。

## 验收

- 默认 Java 不是 21 时，自检快速失败并给出可执行反馈；
- 切换到 JDK 21 后，自检能够验证 Java 与 Maven Wrapper；
- `AGENTS.md` 提供无需聊天上下文即可发现的入口；
- GitHub Actions 在 `verify` 前调用仓库内的环境自检；
- 完整 `verify` 通过；
- 文档明确区分“环境契约已建立”和“干净机器冷启动已实际验证”。
