# 决策卡 014：重新打开单个任务

状态：已批准，待实施

日期：2026-07-28

## 问题

StudyTrack 可以把未完成任务标记为已完成，但用户误操作后无法把该任务恢复为未完成。
当前 `SPEC.md` 没有授权这项产品行为，并且“本版本不包含”中的“恢复”可能被误读为同时
排除了状态回退和已删除任务恢复。

新增状态回退会改变用户可观察的命令协议和验收语义，即使能够复用现有持久化路径，也
属于第三级变更，必须先由人类决定产品边界并完成规格先行。

## 候选方案与取舍

### A. 保持现状

- 收益：不增加写入命令或测试维护成本；
- 成本：用户无法纠正误完成，只能保留错误状态或重新创建任务。

### B. 增加状态切换命令

使用一个命令在未完成和已完成之间来回切换。

- 收益：命令数量少；
- 成本：相同调用的结果依赖当前状态，脚本意图不直观，重复执行也不具备稳定幂等语义。

### C. 增加显式的单任务 `reopen`

只允许把一个已完成任务重新设为未完成。

- 收益：调用者意图明确，可以为已处于未完成状态定义无写入的幂等成功；
- 成本：增加一条需要覆盖损坏数据和持久化失败的写入路径。

选择本方案。

### D. 增加通用状态编辑或批量恢复

- 收益：一次覆盖更多编辑场景；
- 成本：参数、产品边界和失败语义显著扩大，超出纠正单次误完成的最小需求。

## 人类决定

学习者于 2026-07-28 明确批准：采用显式的单任务 `reopen <id>`，把已完成任务恢复为
未完成；已处于未完成状态时幂等成功且不写入。完整命令协议与验收标准以
[`SPEC.md` 2.8 节及 AC-17](../../SPEC.md#28-重新打开任务)为唯一权威。

## 既定边界

- 第一版只重新打开一个明确 ID 的任务，不提供状态切换、通用状态编辑或批量操作；
- 不恢复已删除的任务，不引入软删除、回收站、历史记录或撤销栈；
- 只改变目标任务的完成状态，不改变标题、ID、`nextId`、其他任务或相对顺序；
- 不改变 JSON 格式，不执行数据迁移；
- 继续使用既有 Application、Repository 端口、原子写入和 CLI 错误映射；
- 不改变现有命令、架构边界、依赖、CI、分支保护或智能体权限。

## 第三级流程

1. 本决策卡、`SPEC.md` 2.8 节、AC-17 和执行计划 015 先进入受保护的规划 PR；
2. 规划合并后，由冷启动、无父对话的子智能体在独立功能分支实施；
3. 主智能体审查实现并独立复验定向场景、真实 JAR 和 JDK 21 完整 `verify`；
4. 功能通过受保护 PR 合并，并检查最终 `main` 的远程 `verify`；
5. 只记录已经发生的实施证据；仅在决策卡 011 规定的条件出现时创建独立收尾 PR。
