# 执行计划 015：重新打开单个任务

状态：规划中，待规划 PR

## 目标

实施决策卡 014、`SPEC.md` 2.8 节与 AC-17，为 StudyTrack 增加显式的单任务 `reopen`
用例。本计划只记录实施步骤、风险、验证方法和停止条件；完整产品协议以 `SPEC.md` 为
唯一权威。

规划 PR 合并后，后续实现必须交给无父对话或冷启动子智能体，使其仅凭仓库 Harness
定位并完成工作；主智能体负责审查、复验和流程收尾。

## 实施步骤

### 阶段 1：Application 状态转换

1. 检查 `completeTask` 的既有实现和测试，以对称但独立的用例实现 `reopenTask`；
2. 增加最小结果类型，区分实际重新打开与已经未完成的幂等结果；
3. 只在状态确实改变时调用现有 `TaskRepository.update`，不增加 Repository 方法或修改
   JSON 模型；
4. 为状态转换、幂等、不存在和保留字段增加 Application 单元测试。

### 阶段 2：CLI 协议与组合

1. 增加 `ReopenCommand`，使用 Picocli 解析一个 `long` ID；
2. 在根命令中注册 `reopen`，复用现有服务工厂和数据错误映射；
3. 按 `SPEC.md` 映射结果、标准输出、标准错误和退出码；
4. 增加命令级测试，证明参数解析失败不访问数据，并覆盖成功、幂等和错误路径。

### 阶段 3：持久化与端到端回归

1. 用临时数据文件验证只修改目标任务的完成状态；
2. 通过操作前后字节或 SHA-256 对比验证幂等、不存在、无数据文件、损坏 JSON 和写入
   失败路径的无副作用或失败安全；
3. 通过 `list`、`show` 和 `summary` 验证重新打开后的读取视图一致；
4. 把 `reopen` 纳入现有损坏数据命令矩阵，并保持全部既有命令回归通过。

### 阶段 4：机械门禁与交接

1. 使用 JDK 21 运行相关单元测试和 CLI 集成测试；
2. 构建真实 JAR，验证最小成功、幂等、不存在、无数据文件和损坏 JSON 场景；
3. 运行仓库唯一完整入口 `.\mvnw.cmd verify`；
4. 只把实际执行的命令、结果、哈希和证据边界写入后续实施证据；
5. 由主智能体独立审查和复验后，通过受保护功能 PR 合并并检查最终 `main` 的
   `verify`。

## 风险与控制

- 风险：把 `reopen` 实现为状态切换，重复调用后重新完成任务。
  控制：Application 结果类型和幂等测试明确未完成状态不调用 `update`。
- 风险：重建任务时意外改变 ID、标题、`nextId`、其他任务或顺序。
  控制：Application 记录型 Repository 与真实 JSON 集成测试同时比较保留字段和集合。
- 风险：只断言逻辑结果，遗漏无写入要求。
  控制：记录 `update` 调用次数，并在 CLI/JAR 场景比较文件字节或 SHA-256。
- 风险：复制 `complete` 时遗漏根命令注册、错误映射或损坏 JSON 回归矩阵。
  控制：命令发现、错误路径、损坏数据矩阵和真实 JAR 验收共同覆盖组合入口。
- 风险：为了实现功能顺便引入通用编辑、批量命令或 Repository 新协议。
  控制：保持最小用例；触发下方停止条件时返回主智能体和人类重新决策。

## 验证方法

- Application：验证实际状态转换、无写入幂等、不存在任务以及所有非目标字段不变；
- CLI：验证 Picocli 参数、stdout、stderr、退出码和数据访问次数；
- 持久化：验证成功写入与各失败路径的原文件保护；
- 真实 JAR：用系统临时目录执行 `reopen` 的代表性黑盒场景；
- 完整门禁：JDK 21 下 `.\mvnw.cmd verify`，包含 Checkstyle、JUnit、ArchUnit 和可执行
  JAR 打包。

## 停止条件

冷启动子智能体发现以下任一情况时必须停止并报告，不得自行扩大范围：

- 必须改变 JSON 格式、迁移已有数据或增加 Repository 协议才能实现；
- 必须改变 `ARCHITECTURE.md` 的核心依赖方向或增加外部依赖；
- 规格中的输出、错误优先级或幂等语义无法按现有机制实现；
- 需要修改现有命令行为、CI、远程权限、分支保护或智能体权限；
- 实际需求扩展到状态切换、通用编辑、批量操作、恢复已删除任务或撤销历史。
